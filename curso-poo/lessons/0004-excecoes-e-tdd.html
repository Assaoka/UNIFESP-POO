Aula 4: Tratamento de Exceções e o Ciclo TDD

Nesta aula, dominamos a gestão de erros em tempo de execução e a metodologia de desenvolvimento orientada a testes. Este conteúdo cobre diretamente as Questões 2 e 4 da prova.

1. O que Acontece Quando uma Exceção é Lançada?

Em TypeScript e JavaScript, uma exceção é sinalizada através da instrução throw new Error(...) ou de subclasses customizadas de Error.

Comportamento de Exceções Não Tratadas (Uncaught Exceptions):

Quando uma exceção é lançada e não encontra nenhum bloco envolvente try...catch na pilha de chamadas (call stack):

  • O fluxo normal de execução do programa é imediatamente interrompido (process abort/crash).
  • O runtime (Node.js ou motor do navegador) imprime no console a mensagem de erro juntamente com o stack trace (o rastreamento detalhado de arquivos e números de linha indicando o caminho exato onde o erro ocorreu).
  • O programa NÃO continua a execução normalmente nem encerra em silêncio.

2. Hierarquia de Exceções de Domínio em TypeScript

No material da aula (Aulas 6 e 7 do PDF original), um sistema de biblioteca é modelado com exceções ricas. Veja a transposição equivalente em TypeScript:

// Exceção base de domínio herdando da classe padrão Error
class LibraryError extends Error {
  constructor(message: string = "Erro ocorrido no sistema de biblioteca") {
    super(message);
    this.name = "LibraryError";
  }
}

// Exceções específicas e expressivas
class NonMemberError extends LibraryError {
  constructor(memberName: string) {
    super(`Membro '${memberName}' não está cadastrado`);
    this.name = "NonMemberError";
  }
}

class BookNotAvailableError extends LibraryError {
  constructor(title: string) {
    super(`O exemplar de '${title}' não está disponível`);
    this.name = "BookNotAvailableError";
  }
}

// Tratamento com try...catch
try {
  // Se membro não existe, lança erro
  throw new NonMemberError("Carlos");
} catch (err) {
  if (err instanceof LibraryError) {
    console.warn("Erro de negócio capturado:", err.message);
  } else {
    console.error("Erro inesperado:", err);
  }
}

3. Metodologia TDD (Test-Driven Development)

O TDD é uma prática de engenharia ágil proposta por Kent Beck com um ciclo iterativo estrito conhecido como Red-Green-Refactor:

1. Teste (RED)

Escrever um teste automatizado para a funcionalidade antes de ela existir. O teste falha obrigatoriamente.

2. Código (GREEN)

Implementar o código de produção mais simples possível apenas para fazer o teste passar com sucesso.

3. Refatoração

Melhorar a qualidade, legibilidade e design do código, mantendo todos os testes verdes e seguros.

A Ordem Canônica Inviolável do TDD:

Teste → Código → Refatoração

Nunca se refatora código quebrado, e nunca se escreve código de produção sem o teste prévio que justifique a sua existência.
